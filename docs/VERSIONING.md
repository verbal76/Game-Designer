# Versioning: four different identities

| Identity | What it is | Where it changes |
|---|---|---|
| **Native APK version** | The installed shell: runtime libraries, shell API, permissions, signing. `v1`, `v2`, `v3` are GitHub Releases with an explicit APK file. | Only when a new APK is published. |
| **Application layer** | The Compose UI + ViewModel + design logic (`:applayer` + `:core`). `vN.M` where N is the native generation it shipped for. | Every layer build; delivered bundled in an APK or over the air. |
| **OTA sequence** | A monotonically increasing integer (`bundleVersion`) of signed bundles on a channel (`ota-dev`, `ota-stable`). | Every OTA publish. Anti-rollback compares this number. |
| **Runtime fingerprint** | `k<Kotlin>-c<ComposeBOM>-a<AGP>-s<shellApi>`; a bundle only loads on a shell with the identical fingerprint. | Dependency or shell-API change. |

An OTA never creates a new native major version.

## Why v3 is a new APK

On-device LLM inference needs a richer native contract than shell API 1 had (`LocalLlm.status/select/load/unload`, diagnostics, a selectable model path), and the native libraries must be 16 KB page-size qualified. Shell API 1 -> 2 changes the fingerprint (`-s1` -> `-s2`), so v2-line bundles are rejected by a v3 APK and v3-line bundles by a v2 APK. That is the intended safe behaviour: the v2 channel keeps working for v2 installs only until `ota-dev` is republished with a `-s2` bundle.

## What the app shows

Settings -> About / Diagnostics: APK version, application layer, OTA sequence and name, runtime fingerprint, source short SHA, AI mode (LOCAL LLM or RULES-ONLY), installed model.

## What does NOT need a new APK

Model catalog data (`ModelCatalogData.kt`, regenerated by the `model-catalog` workflow), download/verify/profile logic, the interpretation layer, the generators and all UI. These live in `:core` / `:applayer`.
